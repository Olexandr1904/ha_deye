# Contributing

Thanks for looking. This is a small project with strong opinions; the shortest
way to a merged change is to know them.

## The constraints that are not up for negotiation

These are what the project is, not preferences:

* **No cloud.** No Deye Cloud, no SolarMAN, no external API, no CDN, no
  telemetry. The panel talks to the Home Assistant instance it runs inside and to
  nothing else.
* **No backend and no database.** Recorder and Statistics already exist.
* **No polling.** Data arrives as `state_changed` events. The whole dashboard has
  exactly one interval timer, a 30-second heartbeat.
* **No build step for development, and no npm dependencies.** Plain ES modules
  served as files. `dist/` is generated by `tools/build-dist.mjs` for HACS, which
  copies only `.js` files — that is the one packaging concession.
* **No framework and no charting library.** The charts are ~700 lines of SVG.
* **Nothing hardcoded about your inverter.** No entity ids, no units. Roles are
  described in `js/config.js` and detected or mapped.
* **English interface**, with Ukrainian as a second language. Code, comments and
  commit messages in English.

## Running it

```bash
git clone https://github.com/Olexandr1904/ha_deye && cd ha_deye
./tools/run-tests.sh          # unit tests, then a real headless Chrome
python3 -m http.server 8000 --directory deye-dashboard
open 'http://localhost:8000/index.html?demo=1'
```

Requirements: Node 22 or newer (for the global `WebSocket`), python3, and Chrome
or Chromium. Set `CHROME=/path/to/chrome` if it is somewhere unusual.

Useful query flags: `?demo=1` simulated inverter, `&hour=20` pin the time of day,
`&deye_debug=1` logs, `&deye_range=month` open a period, `&deye_settings=diag`
open a settings tab, `&deye_noauto=1` skip entity detection.

## What a change needs

1. **A test that fails without it.** Put it in the cheapest layer that can prove
   the thing — `tools/test-*.mjs` for anything that is pure logic, the browser
   suite for layout, geometry and the shadow DOM. If a browser check would still
   pass with the feature deleted, it belongs in a unit test with real numbers.
   [docs/test-plan.md](docs/test-plan.md) explains the layers and, more usefully,
   why the defects that escaped escaped.
2. **`./tools/run-tests.sh` green**, and `node tools/build-dist.mjs` run if you
   touched anything the package contains (CI fails on a stale `dist/`).
3. **A bump of `VERSION`** in `deye-dashboard/js/config.js` for anything users
   will load. It is the cache-busting query; without a bump, browsers keep the old
   code for up to a month.
4. **A CHANGELOG entry** in the same wording you would use to explain the change
   to someone who hit the bug.

## Reporting a bug

The useful report says what you saw, what you expected, and where the numbers
came from — a screenshot of the panel plus the same figure from another source
(the inverter's own app, a Home Assistant history graph, a template sensor) is
worth more than any description. If it is about periods or totals, say which
period, and paste the gear icon → **Diagnostics** → *Copy support report*, which
lists role → entity → raw value → value in the model, with no secrets in it.

## Adding a sensor role

Roles live in one table in `js/config.js`: a key, a group, a kind, a label, and
the keywords that identify it. Add the entry, add the label to both dictionaries
in `js/i18n.js`, and add a case to `tools/test-config.mjs` if the role changes how
detection behaves. Nothing else needs to know.
